# Feather Browser 0.2.4 — Design Spec

**Version:** 0.2.4
**Date:** 2026-10-22
**Status:** Approved

## Goal

Four engine primitive additions that close the most impactful gaps left after 0.2.3:

1. `text-align` inheritance through the style tree
2. `rem` and `%` font-size units resolved to px
3. `<img>` element placeholder rendering
4. Glyph cache flush-on-overflow cap (unbounded growth fix)

None of these require new dependencies or new public APIs beyond what already exists.

## Feature 1 — `text-align` Inheritance

### Problem

`style.rs:32` — `INHERITABLE` is `&["color", "font-size"]`. A child element with no explicit `text-align` always falls back to `Left` even when its parent specifies `center` or `right`. Per the CSS spec, `text-align` is an inherited property.

### Design

Add `"text-align"` to the `INHERITABLE` slice. No other change needed — the existing inheritance machinery already propagates any property in that list.

```rust
const INHERITABLE: &[&str] = &["color", "font-size", "text-align"];
```

### Tests

- `test_text_align_inherited_from_parent`: parent has `text-align: center`, child has no `text-align` — child's computed `text-align` must be `Value::Keyword("center".into())`.
- `test_text_align_child_override_beats_inherited`: parent has `text-align: center`, child has `text-align: left` — child keeps `left`.

## Feature 2 — `rem` and `%` Font-Size Resolution

### Problem

`css.rs` already parses `Unit::Rem` and `Unit::Percent`, but `style.rs` only resolves `Unit::Em`. A `font-size: 1.5rem` or `font-size: 80%` value is stored unresolved and falls through to layout/render as-is, causing incorrect sizing.

### Design

Extend the resolution block in `style_tree_depth` (currently at `style.rs:42–48`) with two new branches, executed after the `em` branch so all three share the same `parent_px` lookup:

```rust
// rem: n × root_px. Root font-size is not yet tracked; 16px is the CSS spec default.
if let Some(Value::Length(n, Unit::Rem)) = properties.get("font-size").cloned() {
    properties.insert("font-size".to_string(), Value::Length(n * 16.0, Unit::Px));
}

// %: n/100 × parent_px.
if let Some(Value::Length(n, Unit::Percent)) = properties.get("font-size").cloned() {
    let parent_px = match parent_props.get("font-size") {
        Some(Value::Length(px, Unit::Px)) => *px,
        _ => 16.0,
    };
    properties.insert("font-size".to_string(), Value::Length(n / 100.0 * parent_px, Unit::Px));
}
```

**`rem` base is always 16 px** until a future version tracks the root `<html>` element's computed font-size. This is documented in code and in the Known Limitations section of the README (to be updated alongside this work).

### Tests

- `test_rem_font_size_resolves_to_px`: `font-size: 2rem` → `Value::Length(32.0, Unit::Px)`.
- `test_percent_font_size_resolves_relative_to_parent`: parent `font-size: 20px`, child `font-size: 80%` → child `16.0px`.
- `test_percent_font_size_fallback_when_parent_unset`: no parent font-size, child `font-size: 50%` → `8.0px` (50% of 16px base).

## Feature 3 — `<img>` Placeholder Rendering

### Problem

`<img>` elements have no special handling in layout or render. They produce a zero-height block box and are invisible. Every real HTML page contains images; a missing placeholder makes layout look broken.

### Design

**Layout (`layout.rs` — `layout_block`):**

When the styled node's element tag is `img`:
- Read `width` and `height` from the element's HTML attributes, parse as `f32`. Default to `100.0` and `50.0` respectively if absent or unparseable.
- Set the block's content dimensions to those values directly; skip child layout entirely.
- Return immediately — no children to process.

```rust
if tag == "img" {
    let w = attr("width").and_then(|s| s.parse::<f32>().ok()).unwrap_or(100.0);
    let h = attr("height").and_then(|s| s.parse::<f32>().ok()).unwrap_or(50.0);
    d.content.width  = w;
    d.content.height = h;
    return;
}
```

**Render (`render.rs`):**

When rendering a block box whose element tag is `img`:
1. Fill the content rect with a light grey: `CssColor { r: 180, g: 180, b: 180, a: 255 }`.
2. Draw a 1-px darker border: `CssColor { r: 140, g: 140, b: 140, a: 255 }`.
3. If the element has a non-empty `alt` attribute: render the alt text centered horizontally, vertically centred, at 12 px, in `CssColor::DARK`. Clamp to the box — no text overflow.

The placeholder is intentionally minimal: it signals "image here" without requiring any image decoding infrastructure.

### Helper

Both layout and render need to know the element tag and attributes. The `BoxType::Block(StyledNode)` variant already carries the full `StyledNode`; `StyledNode.node` is `Node`, and `Node.node_type` is `NodeType::Element(ElementData)` which has `tag_name` and `attributes`. No new types needed.

### Tests

- `test_img_layout_default_dimensions`: an `<img>` node with no attributes produces a block box of `100.0 × 50.0`.
- `test_img_layout_explicit_dimensions`: `<img width="200" height="80">` produces `200.0 × 80.0`.
- `test_img_layout_partial_attributes`: `<img width="60">` produces `60.0 × 50.0` (height default).

Render tests remain pixel-level in `engine_render_test.rs`:
- `test_img_placeholder_paints_grey_fill`: renders an `<img>` box; the canvas pixels in the content rect are grey (`r: 180`).

## Feature 4 — Glyph Cache Flush-on-Overflow

### Problem

`font.rs:30` — `GLYPH_CACHE` is an unbounded `HashMap<u64, Arc<GlyphBitmap>>`. A long-running browser session that encounters many distinct `(char, font_size)` pairs grows this cache without bound.

### Design

Add a capacity constant and a guard at the top of `rasterize_cached`:

```rust
const GLYPH_CACHE_CAP: usize = 512;

pub fn rasterize_cached(&self, ch: char) -> Arc<GlyphBitmap> {
    let key = (ch as u64) << 32 | self.size.to_bits() as u64;
    GLYPH_CACHE.with(|cache| {
        let mut map = cache.borrow_mut();
        if let Some(g) = map.get(&key) {
            return g.clone();
        }
        if map.len() >= GLYPH_CACHE_CAP {
            map.clear();
        }
        let g = Arc::new(self.rasterize(ch));
        map.insert(key, g.clone());
        g
    })
}
```

**Why flush not evict:** True LRU requires either an external crate or a `LinkedHashMap`. Flush-on-overflow achieves O(1) amortised insert, zero extra memory for ordering metadata, and no new dependencies. The cost of a flush — re-rasterizing the next render frame — is one frame of latency at most, which is acceptable. Typical pages use far fewer than 512 distinct `(char, size)` pairs, so flushes will be rare in practice.

### Tests

- `test_glyph_cache_does_not_exceed_cap`: rasterize 513 distinct chars; verify cache length is ≤ 512 after the last call.
- `test_glyph_cache_still_works_after_flush`: after a flush, rasterizing a previously-cached char returns a valid `GlyphBitmap` (no panic, correct advance_width > 0).
